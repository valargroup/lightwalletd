Measured on 2026-09-04. Upstream was fetched again and remained at
`d79cd1100575ff909d70e00d5514a4092df94934`.

This pass remeasured range filtering and the polling/keepalive combination.
Raw-hex, subtree warm-cache, mempool, and direct-stream timing evidence comes
from the [earlier report](2026-09-04-macos-arm64.md); those timings were not rerun.
The previous in-place filter is pinned at
`a19dd4e482664e04a1935d929c287fa45f5c7040`, polling at
`5ab05f156de4c0887be79e4a076f9879425040b7`, and keepalive at
`e352a01c3c3c27017c830bdc2b0cec2f0a330a0f`.

## Decision

The earlier work identifies real improvements, but its headline percentages are
workload-specific. Keep backend connection reuse and the mempool correctness fix
high priority. Keep subtree hash memoization with the no-cache correction below.
Keep direct hex decoding as a large-response optimization. The simpler in-place
range filter remains the conservative general change. The rejected direct-stream
rewrite should remain rejected; nothing here removes the useful producer channel.

A new selective-decoding branch delivers a materially larger range improvement
when requests exclude substantial transaction data. It is a promising experiment,
not a universal replacement for the simpler filter. Do not advance the previous
poll-cache branch unchanged: it changes the meaning of the reported tip, and it
does not cache the explicit `GetTreeState` path used by the SDK.

## New range candidate

`adam/lwd-perf-selective-decode` at
`32a8479888e29f716c604abe5c224c6a52fafa50` filters the checksum-verified disk buffer
before protobuf decoding. It avoids allocating excluded components and avoids
allocating replacement transactions. It adds no response cache or cache-memory
budget. The original backend fallback, range continuity checks, and channel remain.

The comparison used the same eight concurrent gRPC clients, 32-block ranges,
three five-second samples per variant, and server `GOMAXPROCS=2`.

| Workload | Upstream ranges/s | In-place ranges/s | Selective ranges/s | Selective vs upstream | Selective vs in-place | Allocated bytes/range vs upstream |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Mixed pools, Sapling requested | 383 | 397 | 524 | +36.6% | +31.9% | -46.3% |
| Mixed pools, default requested | 427 | 438 | 456 | +6.7% | +3.9% | -20.6% |
| Segregated pools, default requested | 1,155 | 1,290 | 2,082 | +80.3% | +61.4% | -74.6% |
| Orchard only, default requested | 748 | 819 | 790 | +5.6% | -3.6% | -22.8% |

The segregated workload reduced median latency from 6.52 to 3.63 ms and server
CPU per range by 43.8%. The Sapling-only workload reduced CPU per range by 26.3%.
However, mixed-pool default requests saw p95 worsen from 30.35 to 38.06 ms despite
higher throughput. The Orchard-only control was 3.6% slower than in-place filtering.
Those counterexamples are why this is not an unconditional recommendation.

All 36 final range samples completed with zero RPC errors. Every completed request
returned exactly 32 blocks and the same serialized response size as the corresponding
baseline. Unit tests additionally compare message contents across all 16 pool
combinations, real checked-in block fixtures, unknown fields, empty transactions,
cache ownership, and replacement after a reorg. The full Go suite and targeted race
tests pass. Skipped components retain structural wire validation, and a schema test
guards the implementation's assumptions about component fields.

The initial unlimited-parallelism prototype showed a larger Sapling speedup but
lacked the final skipped-component validation. Those preliminary results are not
used in the table. Final data is preserved in
[`2026-09-04-followup-ranges.jsonl`](2026-09-04-followup-ranges.jsonl).

## Polling assessment

The original `poll` operation cycles `GetLatestBlock`, `GetLatestTreeState`, and
`GetLightdInfo`. The SDK snapshot inspected at
`d2e036a2492862e5ec4d66ed3c3beaf5446b53d4` instead explicitly calls `GetTreeState`
with the height from `LightdInfo` in its NU6.3 server validation. The old optimization
leaves that method unchanged. The new `wallet-poll` workload substitutes `GetTreeState`
for `GetLatestTreeState`; it is a status-path comparison, not a full wallet replay.

The confirmation adds a fixed 2 ms delay per backend RPC, uses eight clients and
server `GOMAXPROCS=2`, and takes three six-second samples per variant. This delay
is controlled input, not an estimate of real node latency.

| Variant | Requests/s | p50 ms | Backend RPCs/sample | Backend RPCs/client request | Backend connections/sample |
| --- | ---: | ---: | ---: | ---: | ---: |
| Upstream | 1,956 | 3.364 | 15,665 | 1.334 | 15,665 |
| Keepalive | 2,167 | 2.993 | 17,353 | 1.334 | 8 |
| Previous poll cache | 7,121 | 0.227 | 14,256 | 0.334 | 14,256 |
| Poll cache + keepalive | 7,658 | 0.234 | 15,328 | 0.334 | 8 |

The earlier cache is still a substantial improvement: 3.64x
throughput and approximately 75% fewer backend RPCs per completed status request.
But it still performs one `z_gettreestate` for each explicit tree-state request.
The 7.5% extra throughput from combining it with keepalive confirms
that the optimizations complement each other. At saturation the remaining tree
queries keep total backend requests high; the earlier “single-digit RPCs” result
does not describe this endpoint mix. All twelve samples completed without errors.

The combined measurement uses a detached experimental composition at
`cd6dabb01709f8247f1086b30acbbee08de2f5c2` (the original poll branch plus the original keepalive commit).
Raw results are in [`2026-09-04-followup-poll.jsonl`](2026-09-04-followup-poll.jsonl).

There is also a semantic change independent of the benchmark. The protocol says
`GetLatestBlock` returns the tip of the best chain. The old branch substitutes the
highest block in the disk cache, which can lag the backend during initial ingestion,
catch-up, or ingestion failure. The atomic height/hash snapshot is useful, but
atomicity does not establish freshness. Preserve the backend-tip contract with
bounded refresh/coalescing, or explicitly agree on a different contract before
advancing this branch. Its existing tests advance the local cache; they do not
establish equivalence when the backend moves ahead of that cache.

## Subtree correction

The memoization branch calls through the disk-cache pointer unconditionally,
although `--nocache` intentionally supplies no cache. A separate local branch,
`adam/lwd-perf-subtree-nocache` at
`c198a29840cae3ea710fefca70cc8836f7f1518b`, restores the existing backend metadata fallback.
Its successful no-cache response test and targeted race tests pass, as does
`go test ./...`. This correction does not change the warm-cache optimization.

## Measurement limits and harness changes

These remain local synthetic experiments on the M3 Ultra with Go 1.25.0, not
public-server capacity estimates. `GOMAXPROCS=2` limits server Go parallelism; it
is not a dedicated two-vCPU machine or CPU quota. Other host activity can affect
absolute rates. Three repeats establish useful signals, not production confidence
intervals. Allocation and CPU-per-request measurements help distinguish reduced
work from timing noise.

Each cache contains 2,048 blocks. The original mixed fixture puts all four pools
in every transaction. The segregated fixture has 55 transparent, three Sapling,
and six Orchard transactions per block; the control has 64 Orchard transactions.
These are deliberately different shapes, not measured mainnet distributions.
The tiny cache index also differs from a mainnet-sized server's live heap. Before
choosing the more complex decoder for general deployment, replay a representative
real cache with a realistic index size, pool mix, concurrency, and tail-latency budget.

The load client now stops starting requests at the deadline and drains active
requests, with a 30-second bound. It counts all RPC errors rather than suppressing
arbitrary cancellation/deadline statuses. Throughput includes the drain time.
A focused test verifies both a successful late completion and a real server timeout.
The final range and polling measurements use this behavior.

`followup.sh` and the README document the reusable matrix, generated shapes,
server-only Go parallelism, and polling endpoint selection. No public servers were
load-tested, no resources were provisioned, no branches were pushed, and no PRs
were opened.
